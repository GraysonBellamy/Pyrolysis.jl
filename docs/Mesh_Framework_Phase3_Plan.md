# Mesh framework: Phase 3 implementation plan (the cutover)

**Scope.** The implementation plan for Phase 3 of the mesh-framework design (`docs/Mesh_Framework_Design_2026-10-17.md` §6, "Cutover"), written against branch `phase2-review` at `f54a6fb` (tree `b544f02`) with the owner's pending gate-table commits in the working tree, after reading the design, the Phase 1 plan, gate and review, the Phase 2 plan, gate, review and followup plan, the decision review of 2026-10-20 and the independent review of 2026-10-21, and revised after a review of its first draft (§1.5). Phase 3 makes the finite-volume core the only core: it probes the architecture's multi-D readiness on a production path before anything is deleted, ports what the old core's consumers still need, states the burnout path's supported envelope, deletes the old core in one pull request, rewrites the guides, regenerates the verification report, and records the end-to-end comparison the design asks for. It also carries the items Phases 1 and 2 scheduled for the cutover: the `FBDF` switch (MF) when its upstream release exists, the layer-scaled correction time (R27), the design's errata, and the independent review's conditions for calling the package research-ready.

**Conventions.** `file:line` refers to `f54a6fb`. "§3.x" without a document name is a section of the design document; "plan §n" is the Phase 1 plan, "P2 §n" the Phase 2 plan. Departures and conflicts continue Phase 2's series: departures from **D110**, conflicts from **C100**. Case ids are the verification cases under `test/verification/cases/`. "The old core" is `src/Solver`, `src/Jacobian`, `src/Discretization`, `src/Residual`, `src/Adaptivity`, `src/Experimental`, `src/Diagnostics`, `src/Geometry` and the state files of `src/Problem`; "the new core" is `Meshes`, `States`, `Kernels`, `Closures`, `Assembly`, `Deactivation`, `ColoredJacobian`, `Integration`, `Outputs`.

### 1.3 What users of the old core have that the new core lacks

From `src/Solver/solve.jl:502-556` against `src/Integration/solve.jl` (`_SOLVE_KEYWORDS`) and `src/Outputs/solution.jl`:

- **Keywords without a counterpart:** `progress` (a ProgressMeter bar; the new core accepts and ignores it, C38), `warm_start` (a prior solution as the initial state), `diagnostics`/`diagnostics_stride` (the Diagnostics log in `extras`), `verify_jacobian`, `jacobian`, `integrator` (an algorithm instance with its `linsolve`; the new core takes `integrator_policy` and `linear_solver`), `min_cells` (the new core deactivates to the last cell), `extra_kwargs`.
- **Keywords whose semantics change:** `handle_depletion` → `deactivation`; `depletion_threshold` (a thickness fraction, 0.05) → `threshold` (`ε_m`, a mass fraction, 1e-2; no exact mapping, C9); `linear_solver` (KLU, UMFPACK, Sparspak through LinearSolve) → `StructuredKLU` by default (D62), `UMFPACKFactorization` selectable.
- **Accessors on the solution, and where their semantics differ:** `get_profile`, `get_cell_positions`, `interpolate_solution`, `sol(t)`, `get_times`, `get_temperatures`, `get_concentrations`, `get_gas_generation_rate`, `n_timesteps`, `succeeded`, `Base.show` (`src/Solver/solve.jl:1606-1640`, `src/Problem/pyrolysis_problem.jl:360-460`); `CoreSolution` has `cell_positions` only, the centres at the last saved time (`src/Outputs/solution.jl:447`). The old `get_cell_positions` returns the problem mesh's centres, which are the initial positions (`solve.jl:1628`), different on a moving mesh; the old `sol(t)` returns the old layout's packed state (`pyrolysis_problem.jl:409`); the old `succeeded` is `retcode == :Success` (`:398`), while the new core ends a complete burnout, an interior void and a `min_thickness` stop all with `:Terminated` and an `outcome`. The field set otherwise matches (`t`, `T`, `ξ`, `z`, `surface_T`, `mass_loss_rate`, `retcode`, `solve_time`, `raw_solution`, `extras` with the same series names, D34), and adds `m`, `correction_velocity`, `cell_centers`, `boundary_T`, `boundary_mass_flux`, `boundary_blowing_ratio`, `events`, `outcome`, `statistics`. C115.
- **Mesh construction:** `create_uniform_mesh(L, n, Val(NC))`, `create_stretched_mesh`, `create_mesh_from_nodes` build a `Mesh1D{NC}` that carries the cell states (`src/Geometry/mesh.jl:41-66`); `apply_initial_conditions!` writes the initial temperature and concentrations into it (`src/Problem/initial_conditions.jl:173-185`); `validate_problem` reads its fields (`problem_validation.jl:102-130`); the adapter reads `cell_states`, `nodes` and `cross_section_area_initial` back out (`src/Integration/setup.jl:382-398`). Radial coordinates are a `setup`/`solve` keyword, not a mesh property (D19).
- **Other consumers:** `parameter_sweep` (`src/Solver/parameter_sweep.jl`, `Distributed`); the plots extension's recipes are typed on `PyrolysisSolution` (`ext/PyrolysisPlotsExt.jl:29`); the precompile workloads solve on the old core; `Internal` re-exports the old modules and none of the new (`src/Internal.jl`); `Material` accepts the tanh `DepletionLimiter`, which the new core converts to the one-sided limiter at setup (D4); a user's conservation check (the `diagnostics` log, TRG chapter 16) has no counterpart on the new core beyond the case recorders of the gate scripts.

### 1.4 Conflicts, with proposed resolutions

**C100. One deletion commit against consumers that must change in the same step.** The design (verdict 7, §6 Phase 3 item 7) wants one deletion commit with the report green before and after; the repository rule forbids a dual path or a shim (plan §9.3). The deletion removes `solve`, `PyrolysisSolution`, the mesh constructors and the exports the examples, the extension, the precompile workloads, the benchmark, `test/perf/` and the suite's routing use, and the guides and API pages cannot be rewritten in the same commit without making it unreviewable. *Resolution:* one pull request (§9.1) with this commit contract: `Pkg.test()` is green at every commit; the docs build, the documentation scan of the grep gate (C114) and the examples' smoke runs are green at the pull request's last commit, and intermediate commits are recorded as not green on those. The deletion commit deletes and renames only (C116): it removes the old modules, makes the new core's `solve` the export, renames the solution type, switches the routing, the extension, the precompile workloads and the benchmark, and ports the examples' `solve` calls. Every numerical change the cutover needs (the native mesh in `setup`, the limiter rename, the property callers moved to the smooth variants, the accessors, the progress observer, `parameter_sweep`, the dependency removals) lands before it, in M2 and M3, as code in the new modules and the shared layers.

**C101. The no-history rule against the end-to-end comparison table.** The design puts a table comparing the new core against the deleted one into the verification report; the owner's rule excludes historical notes from code, docstrings and the guides. *Resolution:* the table is a stamped measurement, as the gate tables are: it is written by a gate script into `test/newcore/gates/measurements/cutover_comparison.md` before the deletion and copied, with its stamp, into one section of the verification chapter the report mode generates (`docs/guide/verification/index.md`), where the Gpyro and FDS overlays already compare the package against other codes. No guide chapter describes the old core. The keyword mapping of Appendix A.4 goes into the pull request's body, not into the guides. Owner question 12.

**C102. The mesh carries the initial state.** `Mesh1D{NC}` holds `cell_states` and takes `Val(NC)` because the old residual read its state from the mesh; the new core's mesh is geometry and tags (`Mesh{1}`: topology and reference positions), and its initial inventories come from the problem's `T_initial` and `ξ_initial` evaluated at the cell centres. *Resolution:* the constructors keep their names and lose the component count: `create_uniform_mesh(L, n; cross_section = 1.0, coordinates = Planar())`, `create_stretched_mesh(…)`, `create_mesh_from_nodes(z; …)` return `Meshes.Mesh{1}`; `PyrolysisProblem` keeps its fields; `setup` evaluates the initial conditions (today's `apply_initial_conditions!` logic as a pure function returning `(T0, ξ0)`); `validate_problem` reads the new mesh; the coordinate system is a property of the mesh (`MeshTopology{D,C}` already carries it), and `setup`'s `coordinates` keyword goes. The first draft of this plan deferred wiring the native mesh into `setup` to the deletion commit on the ground that `setup` could not accept both mesh types; that was wrong: one mesh type per core is one implementation per core, so `setup` takes `Mesh{1}` only from M2, the old `solve` keeps `Mesh1D`, the suite's case builders construct the mesh of the core they run on through one routed constructor in `casedefs.jl` (beside `core_solve`), and the new initial-field path, validation and mesh interpretation run the whole suite and the examples' decks for weeks before anything is deleted. Owner question 10.

**C103. Two `MeshTopology`/`MeshGeometry`.** `Geometry` exports scaffolds of those names at the top level (`src/Geometry/Geometry.jl:53`, `src/Pyrolysis.jl`); `Meshes` defines the production types. *Resolution:* the scaffolds go with `Geometry`; `Meshes`' types take the exports.

**C104. The Phase 0 harness imports the old core.** Nine files under `scripts/mesh_phase0/baselines/` (`ad_overhead`, `common`, `integrator_flag`, `integrator_observer_audit`, `intumescent_ladder`, `jacobian_colors`, `jacobian_common`, `lifted_containment`, `one_callback_parking`) use `initialize_state`, `DirectSolve`, `ApproxSolve` or `residual!`; the harness's contract scripts and its results do not. The design keeps the harness as the Phase 0 record. *Resolution:* the nine baselines are deleted in the deletion commit; `scripts/mesh_phase0/results/` (their evidence) and the prototype-only contract scripts stay and still run. Owner question 11.

**C105. The design's demonstrations need Phase 4's closure and policy, and a layout change.** "The potential closure's per-cell volume balance" is D13's deferred implementation (Phase 4c), "shared-node deactivation by element death" is D25's unbuilt policy (Phase 4), and "N×1 equals the 1D core to round-off" and "skewed-mesh MMS at second order" need a 2D residual through the integrator, which is Phase 4b. The first draft of this plan scoped the demonstrations to the geometry writer, a node count read from the topology, one `D`-generic kernel, the Phase 0 prototype's closure and a masking test; its review showed that this bypasses the question the demonstrations exist to answer: the layout and the assembly assume scalar node positions and one velocity row per node, and the prototype's closure solves a global system (`prototypes.jl:196`) where the design wants cell multipliers as algebraic rows of the DAE with no global solve inside the residual (§3.4). A steady conduction solve and a standalone closure balance can pass while those interfaces stay unsuitable. *Resolution:* W4 is a production-path probe, run first (M1): a small 2D problem through `setup`, `consistent_state!`, `residual!` and `jacobian_pattern` with vector positions, the potential closure's multipliers as algebraic unknowns, the `D`-generic geometry writer and conduction kernel, pattern containment against dense AD, and a moving-geometry test of the discrete GCL and material-frame transport; the full-solve demonstrations become Phase 4b's first week. Its outcome is the second checkpoint of the cutover decision (§2). Owner question 5.

**C106. "Nothing to `main` until the cutover decision" against a 173-commit stack.** P2 §9.1 holds `main` until the owner commits to the architecture; Phase 3's first milestone is that decision. *Resolution:* at M0's go-decision, and once the minimal numerical workflow of W7 runs on pull requests to `main`, the stack merges into `main` in its order (#15 into `mesh-framework-phase2`, #14 into `mesh-framework-phase1`, #12 into `main`), with both cores present and the old core still the default, so nothing user-facing changes; Phase 3's milestones are pull requests against `main`. The alternative (a `mesh-framework-phase3` branch stacked on `phase2-review`, with #12 carrying everything at the end) keeps `main` at 17bc477 for another five months and makes the final review 250 commits. Owner question 2.

**C107. P1 and h-AMR are documented features.** TRG chapter 8 has a P1 section (135 mentions), chapter 14 and UG 10.7 document h-AMR and r-refinement, `test/radiation/` (1,597 lines) tests P1, and `docs/src/api/experimental.md` lists them; `solve` already rejects `P1_QUASI_STEADY` and refuses h-AMR meshes (`src/Experimental/Experimental.jl` docstring), so neither is reachable through the public solve today. *Resolution (recommended):* delete `Experimental` with the old core, cut the P1 section of TRG chapter 8 to a paragraph in its limitations ("not implemented; the lifted-intensity rows accommodate an algebraic `G` block"), delete UG 10.7 and TRG 14.4, and delete `test/radiation/`. The alternative, P1 as an algebraic block on the new core (design question 5), is two to three weeks plus a verification case nothing in the suite needs. Decided at M0 (owner question 3), since W2's port depends on it.

**C108. The Diagnostics module.** The old `solve`'s `diagnostics = true` logs sensible-energy rows through `DiagnosticsCallback`; the module's trackers are driven step by step by `test/discretization/test_conservation.jl` only. The new core reads inventories directly: `total_mass`, the events' vented and lost inventories, the per-step mass ledger of D104 (in V-BO-01's recorder) and the energy ledger of `energy_ledger.jl`. TRG chapter 16 (641 lines) describes the old ledgers. A case recorder inside a gate script is no replacement for a user checking a simulation of their own. *Resolution (recommended):* delete `Diagnostics`, `diagnostics` and `diagnostics_stride`; port the recorder of D104 as a user-facing observer (`ConservationRecorder`, a read-only callback integrating the boundary mass and energy fluxes over each accepted step by Gauss–Legendre, as the burst and ledger gates do) and an audit function (`conservation_audit(sol, recorder)` closing mass and energy against the inventories and the events; without a recorder, the trapezoid on the saved series, which is what the old core's ledger was); rewrite chapter 16 around them. Decided at M0 (owner question 4).

**C109. The calibrated examples were fitted on the old core.** The white-pine inverse (`examples/inverse_analysis/`, Nelder–Mead on the old core's `KenCarp4` with Sparspak, `handle_depletion = false`) and the CAPA driver (local) carry parameters fitted against the old discretization (`S_conv` against the flux-form gas enthalpy, the thickness threshold, the reduced Jacobian's error per tolerance). The Douglas fir deck agrees between the cores to 0.052 K over 60 s (P2 A.8) and the audit decks at matched accuracy to the tolerance, so the drift is expected to be small; it is not zero. *Resolution:* W5 re-runs the white-pine forward at the fitted parameters on both cores (before the deletion, in the comparison script) and reports the drift of its objective and back-face temperature; a re-fit is the owner's, after the cutover. Owner question 16.

**C110. `DepletionLimiter` is a public, documented type.** The one-sided limiter (`OneSidedLimiter`, D4) replaces the tanh one on the new core; `Material` is parametrized on the limiter type and exported `DepletionLimiter(threshold, enabled)` appears in the guides and the examples. *Resolution (recommended):* the one-sided limiter takes the name `DepletionLimiter` with the same constructor keywords plus `join` and `base_scale` at their defaults (plan §12.5), the tanh type is deleted, and `setup`'s conversion goes. The rename lands in M2 with the old core's fingerprint re-run (the old core keeps the tanh limiter's behaviour through the type it is given until the deletion, so the rename is of the new type only, and the old name is freed at the deletion). Decided at M0 (owner question 9).

**C111. `ProgressMeter` and `Distributed` are old-core dependencies.** The progress bar (`src/Solver/solve.jl`, the progress callback) and `parameter_sweep` are user-facing (five examples pass `progress = true`; UG chapter 12 is parameter sweeps). *Resolution (recommended):* port both onto the new core as read-only observers and a wrapper of the new `solve` (the policy's flag rule already covers user callbacks, D40); `progress` then draws again and C38's "accepted and ignored" ends. Decided at M0 (owner question 8).

**C112. **W3. The layer-scaled correction time (R27; M4, time-boxed to three weeks).** The one constant `τ = 720` s was tuned on V-BO-01's 5.9 mm layer; one invocation holds up to about twice it (C98), V-BO-08's 1 mm layer at `ε_m = 3e-2` needs `τ ≤ 360` s (C94), and a 100-cell single layer pays the `N²/τ` gain (R41, a separate lever: at fixed thickness the gain's refinement scaling is untouched by any `τ` rule). Two candidates, and explicit per-layer times as the fallback. **(B, leading)**: `τ_layer` set once per layer at its first activation from the layer's observed thinning rate, `τ_layer = λ · h_layer(t_a)/|ḣ_layer(t_a)|`, an event-time constant that adds one event per layer and is qualified as the located events were (the shift against the tolerance, the restart, admissibility). It satisfies the time-rescaling identity below algebraically, because the thinning rate scales with the physical rates; it is not thereby reliable: the rate at first activation need not predict the remaining activated life when the heating changes afterwards or the layer is heterogeneous, so the ladder includes decks whose physical rate changes after activation (below). Its degenerate cases are defined, and every guard is dimensionless so that none breaks the scaling: a thinning rate at or below a floor set relative to the layer's own scale (`h_layer(0)` over the solve's horizon: the layer not yet regressing; the default `τ` until a later crossing of a second activation threshold re-estimates it once), a positive rate (a swelling layer: the default `τ`, since nothing vanishes), a layer that re-activates after the estimate (no re-estimate), and no absolute cap on `τ` (a cap, if any, is a multiple of the layer's estimated life). **(A, baseline)**: static, set at setup from the layer's initial thickness, `τ_layer = τ_ref · h_layer(0)/h_ref`; it extrapolates one PMMA calibration by thickness and cannot be a scale-aware automatic default, since under the rescaling below the right `τ` scales by `1/s` at unchanged thickness and A's does not; that does not make it unusable inside a measured envelope, so it is kept as the row that shows what thickness alone buys and may be the fallback's default value within its stated range. **The rescaling test** is exact only on a restricted deck, because the surface balance's losses do not scale with the rest (`src/BoundaryConditions/surface_balance.jl`: `q_BC = q_ext − εσT_s⁴ − h(T_s − T_∞)`; re-radiation cannot be scaled, since `ε ≤ 1` and Kirchhoff ties the absorptivity to it): V-BO-01's material and mesh under `RadiativeFluxBC` with the flux scaled by `s`, `ConvectiveBC` with `h` scaled by `s` and no `RadiativeBC`, an adiabatic back, Fickian transport with `λ` scaled, `k` and the pre-exponential factors scaled by `s`, no Darcy mobility, no time-dependent forcing, and `tspan`, `dt` and `saveat` divided by `s`; with those, `T(z, t/s)` and the inventories are identical to the unscaled deck, and the identity is a test of the core on its own (§5.3 item 13) before it is a test of `τ`. The ladder's physical configurations, about sixteen: V-BO-01, V-BO-06, V-BO-07 and V-BO-08 (thickness and composition); V-BO-01's deck at 25 and 50 kW/m² (heating) and at half and twice its pre-exponential factor (kinetics); the restricted deck and its rescaled pairs at `s = 2` and `s = 1/2`; two rate-change decks (V-BO-01's flux stepped down by half and up by half at a time after the layer's first activation, so that the estimate at `t_a` is wrong by a known factor); `ale_darcy` 100 with deactivation (the long layer). The qualification runs are counted apart from the configurations: each burnout configuration at 30, 60 and 120 cells, the three thresholds and the bands of W9 where its row is gated, and reltol 1e-6 and 1e-7 at the CI resolution; the gate document reports both counts. Per run: the invocations, the largest merged fraction, the activated life, `T_sync`, the steps, the QoIs and the burst measures. Acceptance, for either candidate: Phase 2's item 1 on every row that passed before, V-BO-08 at 3e-2 added, the rescaled pairs equal to their unscaled rows in dimensionless time to the tolerance, the rate-change decks within W9's hard criterion, W9's accuracy criteria on the burnout rows, and `ale_darcy` 100's steps reported against the band-only 470; a candidate is promoted only when accuracy and cost both pass. If neither passes by the time box, `τ` stays an explicit per-layer keyword (`EquidistributionCorrection(τ = …)` accepting one value per layer) with a bounded support statement in the user guide (the measured range of activated life over `T_sync` in which one invocation held, with the configurations it was measured on), and R27 goes to Phase 4. ## 11. Summary

**What Phase 3 builds.** The finite-volume core as the only core, in this order: a production-path probe of the architecture's multi-D readiness (vector positions, cell multipliers as algebraic rows, a `D`-generic kernel and geometry, containment, a moving-geometry test) before anything else; the user constructors, the native mesh in `setup`, the solution accessors under a stated specification, a progress observer, parameter sweeps and a user-facing conservation audit, all re-hosted on the new core and run through the whole suite and the examples' decks for weeks; every old-core test's obligations ported or named; the layer-scaled correction time with the activation-time candidate leading and a widened ladder; the burnout path's supported envelope under joint refinement, with accuracy as the hard gate and the invocation count reported; a qualified finite-difference derivative; the end-to-end comparison on a quiet machine with whole-run accuracy budgets and a memory protocol, taken after the last numerical change; the `FBDF` switch when its release exists; then one pull request whose first commit deletes `Jacobian`, `Discretization`, `Residual`, `Adaptivity`, `Solver`, `Geometry`, `Experimental`, `Diagnostics` and the old state files (about 21,500 lines of `src/`, about 16,000 of `test/`) and renames, with bit-identical numerics across it, followed by the rewritten guides, the API pages and the regenerated report, reviewed and fully tested before it merges; a numerical CI gate from the first merge; the design's revision.

**What it costs.** Twenty to twenty-four weeks of one developer with every workstream, fifteen to eighteen with the layer time and the envelope's comparator deferred; a public API change (Appendix A.4) with no shim; the P1 and h-AMR code and the old ledgers gone.

**What its gate proves.** One `Pkg.test()` and the enthalpy suite green at every commit of the cutover; no old-core name in code or documentation; the report regenerated with thirty chapters and the comparison table; the dimension-general interfaces exercised on a production path in 2D with the closure in the DAE; numerics bit-identical across the deletion; time to first solve held; every simulation example running under a named smoke command; the CI gate live; the independent review's six conditions answered; and, where the owner chose them, a layer time that scales with the layer and the burnout path under `FBDF`.

**What remains open after it.** Phase 4: the radial exact cases and radial Beer–Lambert (C37), 2D column mode with the full-solve demonstrations, the general 2D closure and the multi-D correction, element death through a solve, cone geometry, 3D and its preconditioner; the variable cross section's retirement with column mode; the Péclet weighting (C21); V-MMS-03's face temperature (C33); AD through the solve if the owner wants it.
